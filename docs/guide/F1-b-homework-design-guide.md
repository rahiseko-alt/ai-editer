# F1-b: コマ間の宿題設計ガイド

> ロードマップ葉 **F1-b** の成果物。各コマの終わりに、次コマまでの1週間で顧客（受講者側）が
> 自分で行う「宿題」を、何を・どのくらいの粒度で・何のために出すかという設計方法として定義する。
>
> - 宿題の対象となるコマ別到達点は **B1**（コマ別設計表）が正。本ガイドは「到達点をどう宿題へ落とすか」の
>   方法だけを定義する。宿題の**配布・進捗確認の実務**は **F1-a** が正。

---

## 1. 宿題とは何か（増分作業との違い）

- **増分（B2用語）**：別チームが開発する成果物。発注・受入のサイクルで回る。
- **宿題（本ガイドの対象）**：顧客側（受講者本人）が、次コマまでに**自分で**行う準備・確認作業。
  例：現場での実測、社内関係者への確認、簡単な一次情報の収集。
- 宿題は増分の代わりにはならない。**宿題を「開発」の穴埋めに使わない**（スコープクリープの温床になるため、
  開発が必要な作業は宿題ではなく B2 の増分発注に乗せる）。

## 2. 宿題設計の3原則

1. **次コマの到達点から逆算する（DP-1）**：次コマの到達点（B1参照）を満たすために「コマ開始前に揃っていないと
   コマ内で検証できないもの」だけを宿題にする。関連しているが無くても次コマが進められるものは出さない。
2. **1コマ＝1つの宿題（原則）**：複数の宿題を出すと未達の切り分けができなくなる。どうしても複数必要なら、
   優先度を明示し「これだけは必須」を1つに絞る。
3. **完了の基準を宿題を出す時点で決める（DP-5の縮小版）**：「やってみる」ではなく「〇〇が揃っていること」
   という検証可能な形で出す。顧客の自己申告（「やりました」）だけでなく、次コマ冒頭で現物を確認する。

## 3. フェーズ別の宿題の型

| フェーズ | コマ | 宿題の型 | 例 |
|---|---|---|---|
| Ⅰ 診断・設計 | 2–3 | 現状データの収集・関係者確認 | 「対象イシューの直近実績データを次コマまでに用意する」「値引き権限者に確認しておく」 |
| Ⅱ 実装伴走ループ | 4–10 | 増分の現場適用・観察 | 「納品された増分を実際の業務で1週間使ってみて、使いにくかった点をメモする」 |
| Ⅲ 実証・自走化 | 11–12 | 自走準備 | 「引き継ぎ手順書の該当箇所を自分で一度実行してみる」 |

- **コマ1（初回）は宿題を出さない**：初回はロードマップ確定が到達点であり、その場で完結する。
- **コマ6（中間棚卸し）の宿題**：新規の実務ではなく「変更したい点があれば書き出しておく」の1点に絞る
  （B2の再凍結イベントの入力を用意するため）。

## 4. 宿題テンプレート（配布時にこの形で書く）

```
【宿題】<何を>
- 目的：次コマの到達点「<B1の該当到達点>」を検証するために必要
- 完了の基準：<検証可能な形。例：「〇〇の実測値をメモしてくること」>
- 期限：次コマ開始まで
- 次コマでの確認方法：<冒頭で何を見せてもらうか>
```

## 5. チェックリスト（宿題を出す前に）

- [ ] 次コマの到達点（B1参照）から逆算して、無いと次コマが進まないものだけを選んだ。
- [ ] 1つに絞った（複数ある場合は必須を1つ明示した）。
- [ ] 完了の基準を検証可能な形で書いた（自己申告で終わらせない）。
- [ ] 開発が必要な作業を宿題に混ぜていない（該当するなら増分としてB2の発注フローへ）。
- [ ] 次コマ冒頭での確認方法を決めた。

---

## トレーサビリティ

- 本ガイドは **B1**（各コマの到達点）から宿題を逆算する方法を定義したもの。配布・回収・進捗確認の実務は
  **F1-a** が正。開発が必要な作業との切り分けは **B2** の増分の型に従う。
