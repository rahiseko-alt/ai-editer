# F1-c: 別チーム開発への受け渡し確認ガイド

> ロードマップ葉 **F1-c** の成果物。**B2（`docs/design/B2-change-and-dependency-rules.md`）§1「依存の型」**
> を、講師（フォロー担当）が毎コマ末・毎コマ頭に実際に行う**実務手順**として具体化する。
>
> - 依存管理の運用ルール（何を守れば破綻しないか）の正は **B2**。本ガイドはそれを「いつ・何を・どの順で
>   確認するか」というチェックリスト水準まで落としたものであり、ルールそのものを変更しない。

---

## 1. 対象範囲

コマ末に別チームへ増分を発注してから、次コマ（またはそれ以降）で受領・受入判定するまでの、**講師が行う
確認作業**を対象とする。開発そのもの（別チームの作業）は対象外。

## 2. 発注時（コマN末）の確認手順

B2 §1「発注時の必須項目」①〜④が揃っているかを、その場でチェックする。

- [ ] ①対象の葉ID（roadmap上のどのノードに対応する増分か）を明記した。
- [ ] ②受入条件（検証可能な1事実）を、別チームと講師の双方が同じ言葉で理解した（言い換えさせて確認する）。
- [ ] ③期限（次コマ開始まで、または合意した日付）を明記した。
- [ ] ④見積り（幅＋信頼度）を、概算アプリ（D）で算出し添付した。
- [ ] 上記①〜④を `docs/roadmap.html` の該当葉（`deps`／`criteria`）に反映し、PRを出した。

## 3. コマ間（発注後〜次コマ前）の中間確認

- 次コマ前日までに、F1-a のコマ間フォロー連絡と合わせて、別チームから**納品予定に変化がないか**を確認する。
- 変化がある場合（遅延の兆候）は、B2 §5 具体例C の「検知」ステップに従い、次コマを待たずに動く：
  1. 発注時に凍結した受入条件を満たす納品物が、現時点で存在するかを確認する。
  2. 存在しない・間に合わない見込みなら、講師は「未達の可能性あり」を発注側（マスター）へ即共有する
     （次コマ冒頭まで抱え込まない）。

## 4. 受領時（次コマ頭）の確認手順

B2 §1「受領時の必須手順」を、次コマ開始**前**（コマ内時間を使う前）に完了させる。

- [ ] 発注時に凍結した受入条件を**そのまま**用意する（コマ内で緩めない・言い換えない）。
- [ ] 納品物が受入条件を満たすかを、**発注者以外（独立）**が確認する（B2 DP-5。講師自身が発注者を兼ねる
      場合は、受講者側の別の担当者、または独立検証の記録様式に沿って再現手順を残す）。
- [ ] 合否をその場で判定し、roadmap の evidence（合否記録の公開URL/commit）に残す。
- [ ] 合格なら次増分を発注（§2へ戻る）。不合格・未達なら §5 へ。

## 5. 未達・遅延時の切り分け（B2 具体例Cのチェックリスト化）

- [ ] 受入条件は緩めていない（未達は未達のまま記録する）。
- [ ] 未達の葉を open のまま次増分へ繰り越すか、規模が大きい場合は再計画（B2 §5）へ回すかを、その場で判断した。
- [ ] 影響を受ける後続の葉（`deps` で紐づくもの）を洗い出し、先に進められる部分と待ちになる部分を分けた。
- [ ] 新しい納品予定・影響工数を、概算アプリ（D）でレンジ＋信頼度として再算出した。
- [ ] 発注側・受託側で合意できない場合は、意思決定者（マスター）を明示し、起票から実務2日以内に暫定新期限を
      決定・記録した（B2 §5 具体例Cのエスカレーション手順）。
- [ ] 上記の結果を roadmap の該当葉へ反映し、PRを出した（受入条件は変更しない。期限・見積りのみ更新）。

---

## トレーサビリティ

- 本ガイドは **B2 §1・§5 具体例C** を、講師が毎コマ末・頭に実行する手順として落としたもの。
- 対受講者のフォロー実務は **F1-a**、宿題設計は **F1-b** が正。3つを合わせて **F1**（コマ間の伴走ガイド）を構成する。
