# B2: 依存・変更管理の運用ルール（再凍結イベント方式）

> ロードマップ葉 **B2** の成果物。**セッション→別チーム開発→次セッションの依存**／**途中の付け足し**／
> **「解決の定義(100%)」の変更** を、12週間の伴走が破綻しないように回す運用ルールを、**要件変更時の再計画手順の
> 具体例つき**で定義する。
>
> **設計の根拠**は A3 設計原則集（`docs/research/A3-design-principles.md`）：
> - **DP-4 変更は「再凍結イベント」として扱う**（本ルールの中核）
> - **DP-5 反証に開く／本人採点の禁止**（受入は独立に判定）
> - **DP-6 見積りは"点"でなく"幅＋信頼度"**（変更の工数影響は幅で出す）
>
> **重複排除**：進捗・状態・criteria/verify/evidence の正は**ロードマップ（`docs/roadmap.html` の JSON）**。本書は
> その上で回す「運用の型」だけを定義し、個別ノードの中身は二重に持たない。コマ別の目的・到達点は **B1**、
> 概算の計算ロジックは **D**、コマ間の受講者フォロー実務は **F1** が正。

---

## 0. 何を守れば「破綻しない」か（不変条件）

次の5つを常に真に保つ。1つでも破れたら再凍結イベント（§4）に戻す。

1. **変更は黙って積まない（DP-4）**：付け足し・定義変更は必ず再凍結イベントを通す。
2. **受入は本人でなく独立に（DP-5）**：増分の合否は着手前に凍結した受入条件を、作業者以外が再実行して判定する。
3. **見積りは点でなく幅（DP-6）**：変更の工数・期間影響はレンジ＋信頼度で出す（確定するのは構造＝葉、数値は幅）。
4. **依存は道順であって循環しない**：依存は `deps` で表し背骨に置かない。実在ID・非循環は CI（`verify-roadmap-evidence.mjs`）が機械強制する。
5. **各変更は roadmap 差分として残る**：全PRで roadmap 更新が必須（CI 関所 `roadmap-required`）。口頭・別ファイルの変更管理を作らない。

---

## 1. 依存の型（セッション → 別チーム開発 → 次セッション）

コマ間の受け渡しは **「増分（increment）」を単位**とする。増分＝「1コマの発注で別チームが作り、次コマで受け入れる最小の成果」。

- **依存の表し方**：受け入れ側の葉（例 `C-2to12` の各コマ）に `deps` で「対応する増分／先行葉」を張る。時系列は背骨でなく `deps`。
- **発注時（コマN末）の必須項目**：①対象の葉ID ②受入条件（検証可能な1事実＝DP-1）③期限（次コマ）④見積り（幅＋信頼度＝DP-6）。← B1 コマ3の到達点と接続。
- **受領時（コマN+1頭）の必須手順**：発注時に凍結した受入条件で**独立に合否判定**（DP-5）→合否を roadmap の evidence（合否記録の公開URL/commit）に残す→次増分を発注。
- **未達のとき**：受入条件を緩めない。未達葉は open のまま次増分へ繰り越すか、再計画（§5）へ。

---

## 2. 付け足し（スコープ追加）の型 ＝ 親ゲート再オープン

付け足しは「ツリーに子を足す」操作として扱う（＝可変100 の実演）。増やした瞬間、親状態は「子が全 done」でなくなり**自動で検証待ちに戻る**（描画エンジンが導出）。

**手順（付け足し）**：
1. 追加を**新しい葉として起票**（theme を非エンジニアが読める1行で）。
2. `criteria`/`verify` を**着手前に凍結**（DP-5。basis-reviewer が atomic・十分・平易かを第2の目で点検）。
3. `deps` を張る（先行する葉・増分を指す。循環しないこと）。
4. **工数影響を概算アプリ D で再計算**し、幅＋信頼度で提示（DP-6）。
5. **再レビュー → マスター承認**（§4）。承認された瞬間から増分として発注可能。

> 付け足しは「悪」ではなく前提。**黙って作業に混ぜること**だけを禁じる（混ぜると見積りと受入が崩れる＝⑦のスコープクリープ）。

---

## 3. 「解決の定義(100%)」変更の型 ＝ 最重量の再凍結イベント

目標値そのもの（＝顧客が「解決した」と認める閾値）の変更は最も重い。**旧定義で積んだ evidence は失効**し、新定義での再検証が要る。

- 例：初回に固めた「定義100%」（B1 コマ2で数値化）を途中で引き上げ／引き下げる。
- **必ず §4 の再凍結イベント3ステップを通す**。特に「旧 evidence の失効範囲」と「再測定が必要な既 done 葉」を明示する。

---

## 4. 再凍結イベント（共通エンジン：改訂 → 再レビュー → マスター承認）

§2・§3 のすべての変更が通る1本のゲート。**一方通行**（手順化→言語化）で、承認なしに状態は動かない。

| ステップ | 何をするか | 誰が | 記録 |
|---|---|---|---|
| **① 改訂** | 何を・なぜ変えるかを明文化。影響する葉／失効する evidence／新 `criteria`・`verify` を列挙 | 起票者 | roadmap JSON の diff（PR） |
| **② 再レビュー** | 基準の質を第2の目で点検（**basis-reviewer**：atomic・十分・平易か）＋影響葉の受入を独立再判定（**independent-verifier**）。機械で白黒つく所は **CI** | 作業者以外 | レビュー結果／CI run URL |
| **③ マスター承認** | PR を**誰でもレビュー/承認してマージ**。守るのは **CI が緑**なことだけ（tier/basis-gate の承認階層は用いない） | マスター（人手） | マージ commit SHA |

- 承認の階層（tier-0/1/2）や検問所（basis-gate）は**使わない**。ゲートは「CI 緑＋人手マージ」。
- 中間コマ（B1 **コマ6**）は、この再凍結イベントを**定例で棚卸しする回**として置いてある。随時発生分はその場で本イベントを回す。

---

## 5. 要件変更時の再計画手順（具体例）★B2 の verify 対象

### 具体例A：付け足し（コマ4で顧客が対象範囲を拡大）
> 状況：最優先イシューを「1店舗」で解いていたが、コマ4で顧客が「3店舗へ広げたい」と付け足しを希望。

1. **起票**：`C-2to12` 配下（または該当増分）に「店舗2・店舗3への横展開」を新しい葉として起票。
2. **影響の洗い出し**：既存の受入条件・依存への波及を列挙（ベースライン再測定が要るか、既 done 葉に影響するか）。
3. **工数再計算（幅）**：概算アプリ D に「対象店舗数 1→3」を入力し、工数・期間をレンジ＋信頼度で再算出（DP-6）。
4. **ロードマップ更新**：新葉に `criteria`/`verify` を凍結し `deps` を張る。親は自動で検証待ちへ。
5. **再レビュー**：basis-reviewer が新葉の atomic・平易を点検、independent-verifier が影響葉を再判定（§4②）。
6. **マスター承認 → 発注更新**：PR を CI 緑でマージ。次増分の発注（§1）を新スコープで出し直す。
   - ✅ 結果：付け足しが見積り・受入・依存に**反映された状態**で回る（黙って作業に混ざらない）。

### 具体例B：「解決の定義(100%)」の変更（コマ7で閾値を引き上げ）
> 状況：定義100%＝「不良率 2%以下」だったが、コマ7で顧客が「1%以下」に引き上げを希望。

1. **改訂の明文化**：新目標「不良率 1%以下」と、**旧目標で積んだ evidence の失効範囲**（＝2%基準で done とした葉のうち、1%では未達になる葉）を列挙。
2. **測定方法の再凍結**：測定手順・データソースを新目標向けに凍結（B1 コマ2の測定方法を改訂）。
3. **既 done 葉の再判定**：independent-verifier が、失効範囲の葉を新基準で再検証（DP-5）。未達は open へ戻す。
4. **残作業の再計画（幅）**：1%到達に要る追加増分を概算アプリ D でレンジ算出し、必要なら葉を追加（§2）。
5. **マスター承認**：改訂・再判定・再計画を1つの PR にまとめ、CI 緑でマージ（§4③）。
   - ✅ 結果：目標変更が**旧成果の失効と再計画まで含めて**破綻なく反映される。

### 具体例C：依存のズレ（コマ4末に発注した増分2が、コマ5開始までに間に合わない）
> 状況：コマ4末に「増分2」を発注（期限＝コマ5開始まで、受入条件＝『画面Xでデータ入力→保存が成功する』の1事実）。
> しかし別チーム側の事情で納品が遅延し、コマ5が始まっても受領・受入判定ができる状態になっていない。
> 発注側（マスター）と受託側（別チーム）の間で「間に合っている／いない」の認識がズレ、揉め始めている。

1. **検知**：コマ5開始時点で、§1「受領時の必須手順」どおりの独立判定ができるか（＝発注時に凍結した受入条件を満たす納品物が存在するか）を確認する。存在しなければ「未達」と機械的に確定する（間に合った/合っていないの水掛け論にしない＝当初の受入条件が唯一の判定材料）。
2. **未達の扱い（§1原則の適用）**：受入条件は絶対に緩めない。未達葉は open のまま次増分へ繰り越すか、規模が大きければ再計画（本手順）へ回すかをここで判断する。
3. **影響の切り分け**：この増分2に `deps` で依存している後続の葉（例：コマ5で扱う予定だった検証項目）を洗い出し、コマ5の進行を組み替えて先に進められる部分と、増分2待ちでブロックされる部分を分ける。
4. **再計画（幅）**：遅延分の新しい納品予定日を発注側・受託側で合意し、影響工数・期間を概算アプリ D でレンジ＋信頼度で再算出する（DP-6）。旧期限を単に上書きせず、遅延という事実を記録する。
5. **合意できないときのエスカレーション**：発注側・受託側で新しい納品予定日に合意できない場合、双方の主張（希望する新期限とその論拠）と旧期限を記録したうえで、**意思決定者（マスター）を明示**し、起票から実務2日以内に**暫定新期限**を決定・記録する。暫定新期限は本決定ではなく、次の再凍結イベント（§4）で正式化するまでの仮運用値とする。これにより、合意形成の遅延自体が原因で該当葉が計画（期限・担当）を失ったまま放置される事態を防ぐ。
6. **ロードマップ更新**：該当葉の `criteria`/`verify` は変更しない（受入条件は不変）。`deps` は実在ID・非循環のまま保ち、新しい期限・見積り（合意済みまたは暫定）だけを発注情報として更新。evidence は未達のまま空欄を維持する（本人採点で埋めない）。
7. **再レビュー → マスター承認（§4）**：新しい発注情報（新期限・新見積り・影響範囲）をPRにまとめ、CI 緑でマージ。暫定期限を用いた場合はコマ6の定例再凍結で正式な期限へ改めて確定させる。
   - ✅ 結果：発注→受領のズレが「言った/言わない」の水掛け論にならず、**当初の受入条件を唯一の判定基準**として未達を機械的に確定し、影響範囲の切り分けと幅の見積り、合意できない場合のエスカレーションを経て破綻なく次サイクルへ回る。

---

## 6. トレーサビリティ

- 本ルールは A3 の **DP-4（再凍結）／DP-5（独立受入）／DP-6（幅の見積り）** を運用手順に落としたもの。
- 接続先：**B1 コマ3**（発注）・**コマ6**（定例再凍結）／**C-2to12**（増分の受入）／**D**（工数再計算）／**F1**（コマ間の受け渡し実務）。
- 機械強制：依存の実在・非循環と evidence の外部事実性は `scripts/verify-roadmap-evidence.mjs`、roadmap 更新必須は `roadmap-required` が担保する（本書はそれらの前提となる運用の型を定義するだけで、判定は機械と独立検証者が行う）。
