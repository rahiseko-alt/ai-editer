# C-1b: 初回90分 進行台本（顧客の原子レベル解決ロードマップを確定する）

> ロードマップ葉 **C-1b** の設計成果物。**初回90分のコマで、顧客の原子レベルの解決ロードマップが実際に確定する進行**を、
> 時間割り・ファシリテーターの発話・各段の成果物・到達点判定まで落とした「進行台本」。
>
> - 進行の順序は **A3 設計原則**（`docs/research/A3-design-principles.md`）で確定した **DP-2 → DP-3** を固定する。
>   前半＝DP-2（ソフト問題を構造化して「解くべき問題」を合意）→ 後半＝DP-3（合意した枠を MECE に原子分解）。
> - コマ1の枠（役割・所要90分）の正は **B1**（`docs/design/B1-session-blueprint.md`）／空欄テンプレは **B3**（`docs/design/B3-blank-template.md`）。
> - 確定した顧客ロードマップの**正はロードマップ**（`docs/roadmap.html` の JSON）。本台本はそれを確定させる**進行の設計**であって、進捗の正ではない。
> - 本台本が満たす受入（C-1b `criteria`）：**「初回90分のコマで、顧客の原子レベルの解決ロードマップが実際に確定する進行になっている」**。
>   → 本台本は進行の設計を与える。実際に「90分で確定した」という事実は、後段のリモート通しリハ記録（公開URL/録画）を evidence として independent-verifier が判定する（本台本 §7）。

---

## 0. この台本の前提（なぜ90分で"確定"できるのか）

初回で顧客のロードマップを確定できるのは、**確定する対象を2つに分けている**からである（A3 §2 矛盾②の解決）。

- **構造（何をやるか＝スコープの分解）は、この90分で原子まで割って確定する**（DP-1/DP-3）。
- **数値（工数・コスト・期間）は、この場では確定しない**。各葉に「後で幅＋信頼度で見積る」という枠だけ置く（DP-6, コマ2以降・概算アプリ D）。

だから初回のゴールは「**顧客が承認した、原子レベルの"解決ロードマップ（構造）"が1枚に確定していること**」であり、
「工数・費用が確定していること」ではない。ここを混同すると90分では終わらない。**この分離を顧客にも冒頭で明言する**（§2 台本 T-1）。

## 2. 段ごとの進行台本（発話・操作・出口条件）

> 記法：**T-n** ＝ ファシリテーターの発話例（そのまま読める言葉）。**操作** ＝ ボード上でやること。**★出口** ＝ 次段へ進む条件。

### O. オープニング（0–05／5分）

- **T-1（確定範囲の明言）**：「本日90分のゴールは、御社の課題を**分解した"解決の地図"を1枚に確定**することです。
  “何をやるか”の構造は今日ここで確定します。**費用や工数の数字は今日は確定しません**——それは次回以降、幅を持たせて見積もります。今日は"地図"に集中します。」
- **T-2（進め方の予告）**：「前半は、いったん課題を決めつけずに状況を広げて、"本当に解くべき問題"を一緒に一つに絞ります。後半で、それを実行できる粒まで割って地図にします。」
- **操作**：ボードの3面（①状況 ②問題定義 ③地図）を見せ、今どこにいるかを常に示す。
- **★出口**：顧客が「構造は今日確定・数値は後日」に**口頭で同意**した。
- **出口の性質＝非ゲート（前半ゲートはP1-cのみ）**：Oは前半全体（DP-2＝40分）の入口説明であり、単独ではロードマップ確定を左右しない。同意が渋られた場合はT-1を最大2分だけ再説明し、それでも渋られれば同意保留のままP1-aへ進む（前半ゲートはあくまでP1-cの根本定義合意＝R-1で最終判定する）。オーバーした時間はP1-aの冒頭から差し引く（P1-aは15分中13分まで圧縮可、それ以上は圧縮しない）。

### P1-a. 状況を広げる（リッチピクチャ）（05–20／15分）

- **目的**：問題を早く定義しすぎない（A2-⑤ 落とし穴②）。まず状況・関係・利害・不満を非構造に洗い出す。
- **T-3**：「まず"正解"は探しません。今、現場で起きていること・困りごと・関係する人やモノを、思いつくままに挙げてください。つながりや矛盾もそのまま描きます。」
- **操作**：発言を付箋で貼り、人・部門・モノ・情報の流れ・不満（稲妻マーク）を線でつなぐ＝リッチピクチャ。整理しない。
- **問いかけ例**：「誰が困っていますか？」「誰が得をして誰が損をしていますか？」「それはいつ・どこで起きますか？」「なぜ今まで解けていないのですか？」
- **★出口**：関係者・論点・不満が1枚の絵になり、顧客が「だいたい現状はこう」と**うなずいた**（網羅性は問わない）。
- **出口の性質＝非ゲート**：15分で「うなずき」まで届かなくても、P1-bへ進んでよい（リッチピクチャはCATWOEの入力材料であり、前半ゲートはP1-cで最終判定する）。時間超過は最大3分まで許容し、それでも届かなければ「関係者・論点は仮置き」と明言してP1-bへ進む（P1-bで空白があれば都度書き足す）。

### P1-b. 視点を点検（CATWOE）（20–33／13分）

- **目的**：実行者・受益者・所有者・世界観のズレを先に表に出す（A2-⑤ 落とし穴③）。
- **操作**：リッチピクチャから6要素を抜き出して埋める。

  | 要素 | 問い | 記入 |
  |---|---|---|
  | **C** Customers | この改善で得/損をするのは誰か | ＜　＞ |
  | **A** Actors | 実際に手を動かすのは誰か | ＜　＞ |
  | **T** Transformation | 何を→何へ変える中核変換か | ＜入力→出力＞ |
  | **W** Weltanschauung | それを"やる価値がある"とする世界観・前提 | ＜　＞ |
  | **O** Owner | 止める/GOを出せるのは誰か | ＜　＞ |
  | **E** Environment | 動かせない制約（予算/規制/人員/期日） | ＜　＞ |

- **T-4**：「実際に手を動かすのは誰でしょう？　その人にとって、この変更は"やる価値がある"と映りますか？」（W と A のズレを炙り出す）
- **★出口**：6要素が埋まり、特に **T（中核変換）** と **O（承認者）** が一意に定まった。
- **出口の性質＝準ゲート**：C/A/W/Eの4要素は仮置きのまま次へ進めてよいが、**TとOは埋まらない限りP1-cへ進まない**（P1-cの根本定義はTを使い、最終承認はOが行うため、これが欠けるとP1-c自体が成立しない）。C/A/W/Eが13分で埋まらなければ「仮置き」と明言し、T・Oの確定に残り時間を優先する。
- **T・Oが確定しない場合の分岐（時間上限つき）**：残り時間を使っても T（中核変換）または O（承認者）が一意に定まらない場合、**最大3分だけP1-cの頭へ持ち越して確定を試みる**（P1-b/P1-cの境界を最大3分だけ流用してよい）。それでも定まらなければ、**T・Oは「暫定」と明示した上でP1-cへ進む**。
  - **T-4'（暫定運用の必須発話。§出口が自動的にR-1へ落ちるための手続き）**：「中核変換（T）が今の時点では仮決めです。この仮のTのまま先に進めますが、**"仮"だと分かった上で進める**ことをご了承いただけますか？　後半で根本定義を1文にする際、この仮のTでは違和感がある場合は、その場で"確定できていない"扱いに戻します。」
  - この発話により、P1-cのT-5（承認の確認）で顧客が根本定義に同意しても、**その同意が「暫定Tに基づく仮の同意」であることが記録上明示される**。ファシリテーターはP1-cの★出口判定時に「この根本定義は仮のTに基づいていますが、それでも"この地図で確定"と言い切れますか」と**明示的に問い直す**（T-5に必ず追加する一言。単なる★出口の自動判定に任せない）。真の確信付き同意が得られなければP1-cの★出口は不成立＝R-1（前半ゲート未達）として扱い、確信付き同意が得られればTは暫定ではなく確定に昇格する。
  - **O-4'（Oが暫定の場合の必須確認。T-4'と対称の手続き）**：Oが一意に定まらないままP1-cへ進んだ場合、**P1-cの★出口判定（T-5の直後）で、根本定義への同意を今まさに述べた人物がOかどうかを明示的に確認する**：「今『この地図で進める』と仰っていただいたのは、実際にこの実行を止める／進めるを決められるご本人でしょうか？」
    - 確認できた（同意した人物＝O）場合：Oは暫定ではなく確定に昇格し、★出口は通常どおり成立しうる。
    - 確認できない（同意した人物がOではない、またはOが誰か依然として定まらない）場合：**★出口は不成立**とし、Tの確信度に関わらずP1-cの前半ゲートは未達＝R-1（前半ゲート未達）として扱う（Owner確定が曖昧なまま名目上の同意で通過させない）。
  - 以上により、T・Oいずれが暫定のまま持ち越されても、P1-cの★出口判定は自動的にR-1へ合流することが、進行者の具体的な発話・確認手順として保証される。

### P1-c. 問題を1つに絞る（根本定義）＝前半ゲート（33–45／12分）

- **目的**：ソフトな状況から「**解くべき問題**」を1文に固め、顧客と**合意**する（DP-2 の到達点）。
- **操作**：CATWOE を使って根本定義を1文で書く。型＝**「〈Y の手段〉で〈X〉を行い、〈Z〉を達成する」**（do X by Y to achieve Z）。
  - 例：「〈廃棄登録の仕組みと発注ルール見直し〉で〈日次の廃棄を可視化・削減〉を行い、〈廃棄率を下げ利益を守る〉を達成する」
- **T-5（合意の確認）**：「今日この後、地図に落とすのはこの問題です、と言い切れますか？　違和感があれば今直します。」
- **★出口（前半ゲート／必須）**：**顧客（Owner）が根本定義1文に明示的に同意**した。
  → ここが埋まらない限り後半に進まない（§6 リカバリR-1）。合意文をボード②に**確定表示**する。

### 切替（45–48／3分）

- **T-6**：「では前半で合意した"解くべき問題"はこれです（読み上げ）。ここからは、これを実行できる粒まで割って地図にします。」
- **操作**：合意した根本定義を、後半のイシューツリー③の**頂点**に転記する。

### P2-a. MECE に割る（イシューツリー）（48–63／15分）

- **目的**：合意した問題を、重複なく・抜けなく枝分けする（⑥ MECE）。
- **操作**：頂点の問い＝根本定義を「主要因/主要ドライバー」で第1階層に MECE 分割 → 各枝をさらに MECE 分割（第2階層）。
- **T-7**：「この問題を、重ならず・抜けもなく分けると、大きくは何と何に分かれますか？」
- **点検（毎分割ごと）**：「**重複ゼロ・抜けゼロ**ですか？」（A2-⑥ 落とし穴①）。重なったら括り直す。
- **★出口（後半ゲート／必須）**：第1〜2階層が MECE で埋まり、顧客が「この分け方で漏れはない」と**同意**した。
  → ここが埋まらない限り P2-b（原子分解）へ進まない（§6 リカバリR-5）。P2-b以降は全てP2-aの枝の上に積み上がるため、
  MECEな枝が確定しないまま先へ進めると原子性判定そのものが無意味になる。

### P2-b. 原子まで割る（1葉=1事実）（63–75／12分）

- **目的**：各枝の末端を「**独立して落ちうる受入事実ちょうど1つ**」まで割る（DP-1＝本教材の原子性ルール）。
- **操作**：各末端に対して**停止条件の1問**を機械的に当てる：
  > **「この末端の"できたか判定"は、独立して落ちうる受入事実を2つ以上含むか？」**
  > **ちょうど1事実 → 葉として確定。 0事実（受入事実が定義できていない） → 具体的な受入事実を定義するまで確定しない。 2事実以上 → まだ割る。**
- **T-8**：「この枝、"できた/できてない"を1つの事実で言えますか？　2つの別々の合否が混ざっていたら、分けましょう。」
- **各葉に記入**：`到達点（1事実）` と、後で埋める枠として `verify（どう確かめるか）`／`見積り＝後日・幅`（DP-6 の場所取り）。
- **落とし穴対策**：粒度不揃い（A2-⑥ 落とし穴④）を避ける。「概念的に1つ」「だいたい1機能」で止めない（原子性が主）。
- **★出口**：全枝の末端が1事実の葉になり、各葉に到達点が1行で入った＝**原子ロードマップの骨格が完成**。

### P2-c. 検証順を決める（仮説思考／80-20）（75–83／8分）

- **目的**：全部を同時にやらない。**どの葉から着手するか**を、効き目の仮説で決める（⑥ 仮説思考・80/20）。
- **操作**：各葉に「効き目（大/中/小）」と「着手順（1,2,3…）」を付ける。中心仮説＝「ここを直せば一番効く」を1つ立て、**Yes/Noが出る検証**を最初の葉に紐づける（DP-5 反証に開く／確証バイアス回避）。
- **T-9**：「一番効きそうなのはどれでしょう。まずそこを、"効いた/効かない"がはっきり出る形で確かめにいきます。」
- **★出口**：着手順が付き、**最初に着手する葉**が1つに決まった。

### C. クロージング（承認＝ロードマップ確定）（83–90／7分）

- **目的**：answer-first で全体を読み上げ、**顧客の承認**でロードマップを確定する（⑥ ピラミッド原則／DP-3 伝達）。
- **T-10（結論先頭で要約）**：「結論から言うと、御社の課題はこの地図の通り〈N〉個の実行できる単位に分かれ、まずは〈最初の葉〉から着手します。前半で合意した"解くべき問題"を、後半でこの粒まで割ったものです。」
- **操作**：地図を1枚で見せ、①解くべき問題（根本定義）②MECE な枝 ③原子の葉と着手順 を通しで確認。
- **T-11（承認の取得＝最終ゲート）**：「この地図で進めることを、御社として**承認**いただけますか？」
- **★出口（最終ゲート／C-1b 到達点）**：**Owner が"この原子ロードマップで進める"と明示承認**した。
  → 承認の事実（録画/チャットの承認発言/合意メモ）を残し、内容を **`docs/roadmap.html`** の顧客案件ツリーへ描き直す（正の移管）。
  → **Ownerが同席していて、かつ明示承認が得られなかった場合**（明確な反対だけでなく、「今は決めきれない」等の
  **同意保留・態度未決も含む**——★出口は"明示承認"のみを合格とし、それ以外は全てこの分岐に入る）は、
  §6 **R-6** に従う（Owner不在＝R-4とは別の分岐）。

## 6. リカバリ（出口条件を満たせない時の分岐）

- **R-1：P1-c で根本定義に合意できない**（前半ゲート未達）
  → 後半に進まない。残り時間を前半に振り、**問題候補を2つに絞って"次回頭で決める"**を合意して終える。
  この場合の初回到達点は「解くべき問題の候補が2つに絞れた」に縮退し、ロードマップ確定は次回頭へ持ち越す（B2 の再凍結イベントとして記録）。
- **R-2：P2-b で原子まで割り切れない枝が残る**
  → 割れた枝だけ確定し、割り切れない枝は**「次回展開する集約葉」**として1つ残す（遅延展開＝C-2to12 と同じ扱い）。ロードマップは"確定した範囲＋展開待ち1葉"で承認を取る。
- **R-3：時間が押して P2-c/クロージングに届かない**
  → 着手順づけを省き、**「最初に着手する葉だけ」**をその場で1つ決めて承認を取る（最小の確定）。残りの優先順位づけはコマ2冒頭へ。
- **R-4：Owner が同席していない**
  → 承認（最終ゲート）が取れないため、確定は保留。地図までは作り、**承認を非同期で取る期限**をその場で決める（当日中〜翌営業日）。この初回は「承認待ちの地図が完成」に縮退。
- **R-5：P2-a で MECE分割が63分時点で完了しない、または顧客の同意（「漏れはない」）が取れない**（後半ゲート未達）
  → P2-b（原子分解）へ進まない。第1階層（主要因/主要ドライバー）までで打ち切り、第2階層以降の分割は
  **「次回展開する集約枝」**として1つ残す（P2-bのR-2と同じ遅延展開の型）。第1階層だけで顧客の同意を取り直し、
  同意が取れれば縮退した範囲でP2-bへ進む。第1階層ですら同意が取れない場合はR-1と同じ扱い（次回頭へ持ち越し）とする。
- **R-6：Owner が同席していて、かつ地図への明示承認が得られない**（最終ゲート未達。明確な反対・同意保留/態度未決の
  いずれも対象——★出口は「明示承認」のみを合格とするため、それ以外は全てここに入る）
  → まず状況を具体的に言語化してもらう（反対の場合：「何が」「なぜ」承認できないか。保留の場合：「何が決めきれない
  要因か」）。残り時間（Cの7分のうち）で①軽微な修正（葉の言い回し・優先順位の入れ替え等）や、②追加の説明・
  1点だけの確認で解消できる保留なら、その場で地図を直す・説明を補うなどしたうえで再度T-11を1回だけやり直す。
  ③構造そのもの（根本定義・MECEの切り方）に関わる指摘、または④7分内に解消できない反対・保留であれば、
  その場での確定を諦め、**理由（反対点または保留の要因）を明記した「非同期の再承認」**（R-4と同じ様式だが、
  理由欄への記入を必須とする）を設定する。いずれの経路でも、明示承認が取れていない地図をそのまま承認扱いに
  しない（黙って通さない）。

> **O・P1-a・P1-bの★出口は非ゲート／準ゲート**（各段の説明を参照）であり、時間超過は後続段からの時間流用または
> 内容の仮置きで吸収し、単独ではこのセッションを未完了にしない。**このセッションを縮退・未完了として扱うのは
> P1-c（前半ゲート）・原子分解の一部未達・P2-a（後半ゲート）・Owner不在・Ownerの明示承認が得られない・
> 全体の時間切れの6種類の出口未達（R-1・R-2・R-5・R-4・R-6・R-3）が発生した場合に限る。** いずれのリカバリも
> 「黙って延長・黙って持ち越し」にしない。**縮退した到達点を明示して合意**し、B2 の変更管理（再凍結イベント）に載せる。

> **R-1〜R-6のいずれかに入った回は、`C-1b` を未完了のまま扱う。** 縮退した地図・非同期承認・
> 部分的な優先順位づけ・一部枝の次回展開は、いずれも §4 が求める「90分以内に原子ロードマップが
> "そのセッション内で"実際に確定した」を満たさない（直前の段落の6種類の列挙と対象は完全に一致する。
> 元の記述の判定基準は変更せず、新設したR-5・R-6を対象に加え、R-2の記載漏れを是正しただけ）。
> `C-1b` の `evidence` は空欄のまま維持し、§4 の到達点を満たす後続セッション（次回頭での確定、非同期承認の
> 成立等）が成立してから記入する。

## 7. 受入（evidence）の段取り — リハは別途（本セッションでは設計を先行）

C-1b の evidence は「90分で実際に確定した」記録＝**リモート通しリハ（または本番）の公開URL/録画リンク**であり、
機械（CI）で白黒がつかない。よって **independent-verifier** が本台本の到達点（§4）を敵対的に再確認する。

**リハ実施時に決める段取り（本セッションでは未確定・申し送り）**：

- **客役**：誰が顧客（Owner 含む）を演じるか。事前ヒアリング1枚（生の困りごと3〜5行）を用意する役も決める。
- **録画**：通しで録画し、公開可能な URL（限定公開でも第三者が叩ける形）にする。尺で「90分以内」を裏づける。
- **判定**：independent-verifier が録画を見て §4 の各行（90分内/原子性/明示承認/進行の存在）を再確認し、落としにいく。
- **evidence 記入**：リハ成立後、`docs/roadmap.html` の C-1b（および成立すれば C-1a-2）の `evidence` に録画URL/合意メモの公開URLを記入する。

> 本台本（設計）が commit された時点では C-1b の `evidence` は空のまま（リハ待ち）。設計の存在と実演の成立を分けて扱う（§4 の役割分担）。
