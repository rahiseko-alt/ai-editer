## 2026-07-22 handoff が既マージ枝に取り残され次セッションに渡らなかった
- 事象：前回チェックアウトで handoff を、PR#14 が既にマージ済みのブランチ（`claude/language-granularity-verification-6mr28i`）
  先端へ余分に1コミット push（`af0d724`）。PR は既にクローズ/マージ済みのため main に取り込まれず、ブランチ上に取り残された。
  次セッションは main（旧 handoff）から生えたため読めなかった（＝消滅ではなく未マージの取り残し）。
- 根因：handoff が本編（毎PRで必ず main に乗る `docs/roadmap.html`）と別ファイル・別経路。マージ済み枝への追い push は main に届かない。
- 教訓：handoff は roadmap（`meta.handoff`）に同梱し、本編と一緒に必ずマージする。commit/push の自己申告を鵜呑みにせず存否を確認する。

## 2026-07-22 stale なローカル参照を鵜呑みにして「消滅」と誤断定
- 事象：`git cat-file -t af0d724` がローカルで「Not a valid object」を返したのを根拠に「af0d724 は消滅」と断言。
  実際は GitHub 上に実在（上記ブランチ先端）。ローカル clone の `origin/main` も stale（fef4360=Initial commit を指す）で、
  「main は空」とも誤断定した。真の main は cf22e57。
- 根因：ローカルの remote-tracking 参照が古いまま、リモート実データ（`git ls-remote` / GitHub API `list_branches`）で照合せず結論した。
  「本人の自己申告を信じない」を掲げながら、自分のローカル状態を自己申告として鵜呑みにした。
- 教訓：ブランチ/コミットの存否・main の位置は、**ローカルの `origin/*` ではなくリモート実データ**で確認してから断定する。

## 2026-07-22 roadmap-required の必須チェック名を job 名≠登録名で登録し、全PRをブロック
- 事象：`roadmap-required` を必須チェックに登録する際、登録名を **workflow 名**「roadmap-required」にした。だが GitHub Actions
  が報告するチェック名は **job 名**「PRにroadmap更新があるか（例外なし）」。両者が食い違い、必須コンテキスト「roadmap-required」が
  永久に未報告 → roadmap を更新した正当なPRを含め**全PRがマージ不能**（`405 Required status check "roadmap-required" is expected`）。
- 根因：Actions の必須チェック名は **job 名（check run 名）** と一致させる必要があるのに workflow 名で登録した。加えて
  「#17 が blocked」を「必須化が正しく機能」と早合点し、**pass→merge できることを確認せず「検証済み」と報告**した。
- 対処：job の `name` を `roadmap-required` に改名して報告名を登録名に一致させ、roadmap 更新PR(#18)が緑通過→マージ成立で実証。
- 教訓：必須チェックは「**blocked を観測」だけでなく「pass して merge できる**」ことまで実証して初めて"効く"証拠になる。
  GitHub Actions の必須チェックは `jobs.<id>.name` を登録名に一致させる。

## 2026-07-23 粒度ルールの「機械的判定手順」を語の単位を揃えずに書き、合格例と自己矛盾させた
- 事象：AGENTS.md の粒度ルールを「原子まで分解」で AI 解釈がぶれない形へ改訂する際、判定手順を
  ①「verify が『かつ』(=`&&`)で2本以上に割れるか」②「独立2つ以上の理由で落ちうるか」で書いた。だが直後の合格例
  `typecheck && lint && test`（=1葉）に literal 適用すると、①は `&&`×3 で YES、②は型/lint/test の3独立原因で YES となり
  「割れ」＝逆判定。手順どおり読む AI と例に従う AI で結論が割れ、狙い（解釈ぶれ排除）を自壊させた。第2の目(basis-reviewer)が反証。
- 根因：停止条件の真の単位は「独立して落ちうる**受入事実**」なのに、判定手順を「`&&` の数／失敗原因の数」という
  **別の単位**で書いた。事実(fact)と、その検証手段（コマンド）・内部失敗原因(reason)を混同した。
- 対処：判定を「その verify は独立して落ちうる**受入事実**を2つ以上含むか？」の1問へ統一。受入事実＝マスターが独立に
  受け入れ判定したい結果／能力と定義し、複合コマンド=1事実の例と、secret scanning＋push protection=2事実の例を手順内に明示。
  basis-reviewer.md の atomic 定義も同じ1問へ整合。
- 教訓：ルールの「機械的判定」は、数える**単位**を規律本体（=受入事実）と厳密に一致させる。コマンド数・`&&`・失敗原因は
  代理指標であって単位ではない。判定手順を書いたら、必ず既存の合格例に literal 適用して逆判定が出ないか自己テストする。

## 2026-07-23 承認3層化で「審判集合」を狭く定義し、AIが自分のCIを緩められる裏口を開けた（マージ前に第2の目が捕捉）

- 根因：「審判＝審判を動かす仕組み(workflows/scripts)」とだけ捉え、「審判＝緑の判定基準そのもの(scripts本体/config/依存固定)」を
  取りこぼした。守るべき対象を"入れ物"で列挙し"中身"を落とした。特に evidence 検査器が `.github/scripts/` でなく直下 `scripts/` に

- 教訓：「AI が自分の合格を偽造できる経路」を塞ぐときは、審判を動かす仕組みだけでなく**緑の判定基準を決める全ファイル**
  （scripts本体・各config・依存/ランタイム固定）まで含める。パスは思い込みでなく `git ls-files` で実測して被覆を確認する。
  基準を凍結する変更は必ず第2の目に敵対レビューさせてからマージへ回す（今回それが穴を捕捉した＝門が機能した実例）。

## 2026-07-23 branch protection 未設定のまま運用し、赤の tier-2 PR(#26)が手動マージで通った／handoff を tier-2 と束ね余計に手動を増やした
- 事象：tier-1 の bot 登録PR#26 は basis-gate が「tier-2 承認待ち」で赤だったが、**branch protection 未設定のため物理ブロックが効かず手動マージが通った**。
  結果、実稼働未確認の coderabbitai[bot] が tier-1 レビュアーとして main に載る footgun 化。さらに是正+handoff を1つのPR#27に束ねたため、
  本来 master のマージ不要な handoff(tier-0=roadmap meta+failures.md)まで tier-2 に巻き込み、master の手動マージを不要に増やした。
- 根因：①門を「赤/緑の信号」までしか作らず**物理強制(required status check)を有効化しないまま実運用**した＝ソフト信号は人が無視できる。
  ②tier-0(handoff)と tier-2(審判集合の変更)を**1PRに混載**した＝混ぜると全体が厳しい方(tier-2)に倒れ、自動で流れるはずの handoff まで手動化する。
- 対処：handoff を tier-0 単独PRに分離（auto-merge で master 操作なしに main へ）。bot是正(placeholder 戻し)は独立の tier-2 小PRに切り出す。
  次セッション最優先で branch protection を設定し basis-gate 等を必須チェック化（check名=job名一致）。
- 教訓：①門は「信号」だけでは守れない。**物理強制を入れて初めて赤が赤として効く**。②PRは tier をまたいで混載しない
  ＝tier-0(コード/文章/meta)と tier-2(審判集合)は別PRに割る。混ぜると自動で流れる分まで人間のマージ律速になる（＝改革の旨味を自分で消す）。

## 2026-07-23 自作 auto-merge.yml が「対象PRなし」で毎回空振り＝tier-0でも自動マージされなかった（実テストで発覚）
- 事象：tier-0 の handoff PR#28 は全11チェック緑・basis-gate=tier-0 success だったが auto-merge が一度もマージしなかった。実行ログは
  毎回 **「対象の open PR なし。」**＝ PR 一覧取得 `gh api "repos/$REPO/pulls?state=open&base=main&per_page=50" --jq '...'` が
  空を返し、マージ手前で continue/exit していた。結局 Claude が MCP の merge_pull_request で手動マージして handoff を main に載せた。
- 根因：①自作ワークフローの PR 列挙クエリが実環境で PR を拾えていない（`&base=main` 等のクエリ/トークン権限まわりの不備の疑い）。
  実イベントでは走っていた（status/pull_request で発火）ので「発火しない」ではなく「発火後の列挙が空」。②そもそも private 時代の
  自作 auto-merge は GITHUB_TOKEN 起因イベントが別ワークフローを再起動しない制約とも相性が悪く、堅牢でない。
- 対処(方針)：**公開化した今、自作 auto-merge.yml を捨て、GitHub ネイティブの auto-merge + branch protection に置換する**（次セッション）。
  ネイティブは「必須チェック緑で自動マージ」を公式提供し、GITHUB_TOKEN 制約や列挙バグの影響を受けない。＝物理強制(branch protection)と一体で入る。
- 教訓：自動化は「動くはず」で終わらせず**実PRで最後(マージ成立)まで通して確認**する。既製の堅牢機構(ネイティブ auto-merge)がある所を
  自作ワークフローで代替しない（特に GITHUB_TOKEN の再起動制約が絡む領域）。当座は tier-0 を Claude が MCP で直接マージすれば master は不介在。

## 2026-07-24 tier-1 bot の設定ファイル(.coderabbit.yaml)を審判集合から落としかけた／branch protection 物理強制はツールで実行不能と確定

  やろうとして空回りしない）。③承認は `basis-gate`(必須ステータスチェック)に一元化し、GitHub native の Require approvals は使わない

## 2026-07-24 tier-2 の「マスターが自分のPRをApprove」は GitHub 仕様で不可能＝承認導線が破綻していた
- 事象：承認ゼロ化のため tier-2 PR(#30)をマスターに承認させようとしたが、GitHub は**PR作者が自分のPRをApproveできない**仕様。
  当リポの全PRは Claude Code が `rahiseko-alt`（＝マスター本人）名義で作成するため、basis-gate の tier-2「rahiseko-alt の APPROVED で緑」は
  **永久に満たせない**。＝branch protection で `basis-gate` を必須化し Bypass を空にすると、tier-2 は誰にも通せず全ルール変更がデッドロック。
- 根因：basis-gate のtier-2 承認を「GitHub formal Approve」に固定したが、作者=承認者が同一人物になる本運用（AIがマスター名義でPR作成）を
  考慮していなかった。過去の tier-2 PR は実は Approve ではなく**マスターの手動マージ**で通しており（＝承認導線は最初から機能していない）、
  branch protection 未設定ゆえ表面化していなかっただけ。
- 対処：tier-2 の承認＝**マスターが自分でMergeボタンを押す**行為に定義し直す。物理強制は「Bypass list にリポ管理者(マスター)を入れる」
  ＝AI(auto-merge/MCP)は必須チェック赤で物理ブロック・マスターだけが赤いtier-2を意図的にMergeできる、で実現（Bypass空は不可）。
  基準変更を機械承認で完全ロックしたい場合の次善は、Approveの代わりにマスターのコメント/ラベル信号をbasis-gateが読む改修（将来課題）。
- 教訓：承認の「導線」は仕組みを作る前に**実際に人がその操作をできるか**を1回試す。AIがマスター名義でPRを作る運用では formal Approve は
  使えない＝tier-2の合格条件は「作者本人が実行可能な操作」（Merge/コメント/ラベル）で設計する。物理強制は AI を縛り、マスターは Bypass で通す。

## 2026-07-24 承認の階層(tier-1/tier-2＝basis-gate)そのものが過剰＝マスターの使い勝手を破壊していた。廃止して普通のPRフローへ
- 事象：basis-gate による承認3層（変更のたびに「許可が要るか」を判定して止める検問所）を導入して以降、マスターが承認待ちに追われ、
  2日間を消耗。自己承認不可・自作auto-merge空振り・branch protection 手動必須…と副次問題が連鎖し、非エンジニアのマスターには
  理解も運用も不能な複雑さに。マスターの明確な指示により **basis-gate(tier-1/tier-2)を全廃**し、「AIがPRを出す→誰でもレビュー/承認→マージ」
  の一般的なフローへ戻すことを決定。
- 根因：ソロ/少人数・非エンジニアのオーナーという実態に対し、大企業級の多層承認ガバナンスを自作で被せた＝**要件に対して過剰設計**。
  「本人採点の禁止」を突き詰めるあまり、日常の全変更に承認判定を挟み、CI(普通の自動テスト)だけで足りる所を検問所で二重化した。
- 対処：basis-gate 一式（`.github/workflows/basis-gate.yml`／`.github/scripts/basis-gate.sh`／`roadmap-basis-changed.mjs`／
  `basis-reviewers.txt`／`bot-reviewers.txt`／`.coderabbit.yaml`／`docs/basis-gate.md`）を削除、AGENTS.md の「承認は3層」を撤去。
  チェックイン/アウト(handoff)・CI・roadmap-required・evidence 検査は温存。main の branch protection から必須チェック `basis-gate` を
  外すのはマスターの画面操作（ツール不可）。
- 教訓：**ガバナンスは組織規模と運用者のリテラシーに合わせる**。ソロ/非エンジニアには「PR＋CI緑＋誰でも承認→マージ」で十分。
  仕組みが目的化して使い勝手を殺したら、それ自体が最大の失敗。足す前に「この人がこれを毎日回せるか」を問う。

## 2026-07-24 setup.sh の owner/repo 判別を dry-run で修正（先頭2要素→末尾2要素）
- 事象：`scripts/setup.sh` で origin URL からリポジトリを判別する際、パスの「先頭2要素」を owner/repo と
  していたため、プロキシ経由の origin（`http://host/git/OWNER/REPO`）で owner=`git` と誤判定した。
- 根因：GitHub の owner/repo は常にパスの「末尾2要素」なのに、前置きパスの可能性を無視した。
- 対処：末尾2要素（`repo=${path##*/}` / `owner=$(dirname)`相当）を取る方式へ変更。`--dry-run` を先に実行して
  判別結果とペイロードを目視確認してから適用する運用にした。
- 教訓：**外部から与えられる URL は前置き・末尾の揺れを想定して末尾から取る**。破壊的操作（branch protection の
  PUT 等）は必ず `--dry-run` を実装し、対象を目視確認してから本実行する。

## 2026-07-24 「ブラウザ1クリックで branch protection」ボタンが原理的に不可能だった（実リポジトリで露見）
- 事象：新リポジトリの Actions で1クリック実行する `.github/workflows/setup.yml` を追加したが、実際に
  コピーした menu-saas で startup failure（赤×・-1s）。ワークフロー名も出ずファイルパス表示になった。
- 根因：(1) `permissions: administration: write` は GITHUB_TOKEN の有効スコープに存在せず、ワークフローが
  不正で起動失敗。(2) そもそも GitHub Actions の自動トークン(GITHUB_TOKEN)には branch protection を変更する
  権限が無い＝この方式は根本的に成立しない。ローカルの YAML parse は通るため机上では気づけず、実適用を

- 事象：上と同じ回帰テストで、競合状態（ffmpeg が stdout を閉じてから終了するまでの隙）を

## 2026-08-08 verify に「後から自分に都合よく選べる余地」を残したまま基準を凍結しようとした
- 事象：`G-EDITOR` の葉を起票した際、書いた `verify` がレビューで計10件指摘された。型は3つある。
  1. **測っているものが受入事実とずれている**：静止フレームから「その時点で何を話しているか」を

  **文面のレベルで構造的に許してしまう**。とくに 3 は、規律を守っているつもりで破っていた点が悪い。

- 教訓：**`verify` に「既定の」「適切な」「あらかじめ定める」「固定の◯◯を用いて」と書きたくなったら、

  決まっていないということなので、葉として凍結してはいけない。
  自己チェックの問いは「**この verify を、私以外の人が、私の意図を知らずに実行して、同じ合否になるか？**」。

## 2026-08-08 「AとBがそろっていること」を合格条件にしたら、正しい実装まで落ちる基準になっていた
- 事象：時間軸の受入条件（葉H）の4番目を **「出力の映像と音の尺がそろっている」** と書いた。
  検証素材が映像2.000秒／音2.000秒でそろっていたので緑になり、気づかなかった。
  ところが `basis-reviewer` が **映像が音より0.133秒長い普通の素材**（15fpsで32コマ＝2.133秒＋音2.000秒）を
  作って工程に通したところ、**出力は1マイクロ秒も変わっていないのに、この条件だけが落ちた**。
  この条件が測っていたのは「工程がずらしたか」ではなく **「入力が偶然そろっていたか」** だった。
  実際、このロードマップ自身が別の素材について「映像は音声より0.030秒長い」と書いている。
- 根因：前項で「要素どうしの関係を見る条件を置け」という教訓を立てた直後に、
  **その関係を「絶対値」で書いた**。工程が守るべきなのは「映像と音のずれが**入力から変わらない**」ことで、
  「ずれが**ゼロである**」ことではない。**保存されるべき量と、たまたま今ゼロの量を取り違えた。**
- 対処：条件を `abs((出力の映像−出力の音) − (入力の映像−入力の音)) < 0.005秒` に直した。
  上の素材で、旧基準は0.133秒差で落ち、新基準は0.000秒で通ることを実測で確認した。
  2倍速を仕込む壊し方では新基準も落ちる（入力+0.000秒 → 出力−1.000秒）ことも確認した。
- 教訓：**工程の受入条件は「入力に対して何が保存されるか」で書く。「出力が特定の値になること」で書かない。**
  出力の絶対値で書くと、検証素材がたまたまその値だったときだけ通る基準になり、
  **正しい実装を落とし、かつ素材を変えると意味が変わる**。
  関係を測るときは、まず「この関係は入力によって変わってよい量か」を問う。変わってよいなら、
  測るのは関係そのものではなく **関係の変化量** である。

  消えた違いのどれかが受入条件の対象なら、その正規化は使ってはいけない。
  安定した比較のための整形と、検出したい差を消す操作は、見た目が同じで意味が正反対である。

- 根因：**指摘された条件だけを直し、同じ型の穴が空いている他の条件へ広げなかった。**

- 対処：葉Aにも同じ導出を入れ、区切りをまたぐ長さ（340コマ）でも素顔が0件であることを確認するようにした。

- 教訓：**教訓を書いたら、その場で「この教訓が当てはまる箇所」を全部数え上げてから閉じる。**
  教訓を文章にしただけでは適用されない。書いた直後に、
  **同じ性質を持つ条件の一覧を作り、1つずつ照合する**ところまでを1回の作業とする。
  「今回の指摘箇所を直した」で終えると、同じ穴が別の場所に残り続ける。

## 2026-08-08 失敗時の後始末を、処理の前半にしか入れていなかった
- 事象：モザイク工程は「全部作ってから、まとめて確定する」二段構えにしてある。
  失敗したときに素顔と加工済みが混ざらないよう、**前半（モザイクを焼く段）には後始末**を入れていた。
  ところが**後半（素顔を退避する段）には入れていなかった**。
  退避の途中で落ちると、`x-mosaic.mp4` / `y-mosaic.mp4` / `y.mp4` が並ぶ
  ——まさに二段構えが防ごうとしていた混在——が成果物フォルダに残る。
  ファイルの移動は、ウイルス対策のロックや権限で普通に失敗する。
- 根因：**「失敗しうる所」を、失敗が目立つ所（外部プロセスの実行）だけで数えた。**
  ファイルの移動は成功して当たり前という前提が入り、そこに後始末が要るという発想が出なかった。
- 対処：後半にも後始末を入れ、途中まで動かしたファイルを元へ戻し、作った加工済みを消すようにした。
  退避先を塞いで2本目の移動だけを失敗させるテストを足し、後始末を外すと落ちることを確認した。
- 教訓：**「途中で失敗したら元へ戻す」を入れるときは、処理の全区間を数える。**
  外部プロセスの実行だけでなく、ファイルの作成・移動・削除・書き込みも失敗しうる。
  区間の途中に「もう戻せない点」を作らない。
  そして**後始末そのものにも、それが要ることを示すテスト**を置く（無いと、後から消されても気づけない）。

## 2026-08-08 長い動画を区切って処理する所で、顔の追従がリセットされ素顔が漏れていた（本物の不具合）
- 事象：顔モザイクは「顔を見失ったコマを直前の位置で埋める」保持（8コマ分）を持っている。
  ところが長い動画を300コマごとに区切って処理する際、**区切りごとに追従をやり直していた**ため、
  保持が境目で必ず切れていた。区切りの直後で顔を見失う場面を作ると、
  **先頭3コマが未加工のまま出力された**（顔の領域の差が20＝圧縮ノイズだけ。隠れていれば162〜194）。
  15fpsなら20秒ごと、30fpsなら10秒ごとにこの窓が開く。
- 根因：分割処理を後から足したときに、**区切りをまたいで引き継ぐべき状態があること**を数えなかった。
  検証素材は「全コマで顔がはっきり見える絵」だったので、保持そのものが一度も試されていなかった。
  長さだけを実装から導出しても、**素材の中身が盲目**なら経路は測れない。
- 対処：追従状態を区切りをまたいで持ち越すようにした。検証素材に
  「顔が一瞬見つからない区間」を2か所（真ん中＝対照、区切りの直後＝本命）置き、
  区間内の**一番隠れていないコマ**で判定するようにした（最大値で判定すると、
  区間の一部だけ隠れていれば通ってしまう。実際、最初にそう書いて素通りさせた）。
- 教訓：**検証素材は「長さ」だけでなく「中身」も、測りたい事実が壊れる場所から決める。**
  素材が常に理想的（顔が常に見える／音が常に鳴っている／データが常に揃っている）なら、
  「うまくいかないときの処理」は一度も動かない。
  区間の合否を集約するときは、**最大ではなく最小（一番悪いコマ）で判定する**。

## 2026-08-08 失敗の起こし方を1種類に固定していたので、別の壊れ方が2つ残っていた
- 事象：「途中で失敗しても素顔と加工済みが混ざらない」を、
  **読めないファイルを渡す**という1種類の失敗の起こし方だけで確かめていた。
  別の起こし方で試すと、2つの穴が出た。
  (1) **書き込みが途中で止まった場合**（容量不足に相当）：
  失敗した本人の出力は「作れた一覧」に積まれないため後始末の対象外で、
  壊れた `-mosaic` が素顔の隣に残った。納品は `-mosaic` の方をコピーする案内なので、
  **壊れたファイルをそのまま渡す経路**になっていた。
  (2) **途中で切れた動画を渡した場合**：読み出し側の ffmpeg が警告を出しながら
  **終了コード0を返す**ため、終了コードだけを見ていると短くなった動画を成功として書き出す
  （30コマの入力から13コマだけ読めた状態で「出来ました」と報告していた）。
- 根因：失敗の起こし方を、**一番作りやすいもの1種類**で代表させた。
  その1種類では「書きかけが生成される」状態にならないので、(1) は原理的に見えない。
  (2) は「終了コードが0以外＝失敗」という前提を疑わなかった。
- 対処：失敗の起こし方を3種類（読めないファイル／書き込みが途中で止まる／途中で切れた動画）に増やし、
  それぞれで後始末と失敗報告を確認するようにした。読み出し側の警告を握りつぶさず、
  出力があれば失敗として扱うようにした。
  (2) のテストには「この切り詰め方が本当に終了コード0のまま失敗する状態か」を先に確かめる対照を付けた
  （素材が変わってこの前提が崩れると、別の防波堤で落ちるだけになり、測っているつもりで測っていない状態になる）。
- 教訓：**「失敗したときの振る舞い」は、失敗の起こし方ごとに別々に確かめる。**
  起こし方によって「どこまで進んでから失敗したか」が変わり、後始末すべきものも変わる。
  1種類で代表させると、その1種類では到達しない状態が丸ごと未検証で残る。
  そして**外部プログラムの終了コードだけを成否の判断にしない**。
  警告を出しながら成功を返すものがある以上、出力（標準エラー）も判断材料に入れる。

## 2026-08-08 直したつもりの不具合が半分しか直っておらず、短い試し方では差が出なかった
- 事象：区切りの境目で顔の追従が切れる不具合に対し、追従状態を持ち越すよう直した。
  ところが **区切りの重なり（先読み）ぶんを次の呼び出しで作り直す**作りのため、
  同じコマの検出が2回取り込まれ、**顔を見失った回数が二重に数えられて**いた。
  保持の予算（8回×3コマおき＝24コマ）が、境目でだけ18〜20コマへ縮む。
  検証は6コマの見失いでしか試していなかったので、**直ったように見えていた**。
  24コマ見失わせると、一本通しでは素顔0コマなのに区切りありでは3コマ出た。
- 根因：試す長さを「壊れているときに差が出た長さ（6コマ）」で決めた。
  直したあとに確かめるべきは**その仕組みが約束している上限**（保持の予算24コマ）であって、
  たまたま壊れた例ではない。**上限で試さないと、上限が縮んだことは見えない。**
- 対処：重なりの手前の状態を返して持ち越すようにした（重なるコマの検出を二重に数えない）。
  検証の見失いの長さを実装の定数から導き（hold_frames × detect_every）、上限ちょうどで試すようにした。
  実測で、持ち越し無し・不完全な持ち越し・正しい持ち越しの3つが判別できることを確認した。
- 教訓：**「◯◯まで耐えられる」仕組みを検証するときは、その◯◯ちょうどで試す。**
  余裕のある値で試すと、余裕が削られたことに気づけない。
  上限は実装の定数から導き、検証側に直書きしない。

## 2026-08-08 「隠れているか」を1画素で判定していた
- 事象：顔が隠されたかどうかを、顔の矩形の中で**一番差の大きい1画素**で判定していた。
  これだと**顔の端を少し塗っただけの実装でも合格**する。顔の大半が見えていても緑になる。
- 根因：「隠れていない状態」との差が大きく出る指標を選んだだけで、
  **「部分的にしか隠れていない状態」を落とせるか**を考えていなかった。
  最大値は、1点でも条件を満たせば通る指標である。
- 対処：顔の矩形全体の**平均の差**で判定するようにした（塗られた広さが足りなければ下がる）。
  正しく隠れているとき9.57、追従を持ち越さないと2.86、持ち越しが不完全だと3.76と、
  3つの状態が判別できることを実測で確認して、境を6.0に置いた。
- 教訓：**「あるものが覆われているか」を測るなら、最大値ではなく広がりを見る指標を使う。**
  最大値は「どこか1点が変わった」しか言わない。
  合否の指標を選ぶときは、**通ってはいけない中間状態**（半分だけ覆われた状態）を1つ思い浮かべ、
  その状態が確実に落ちるかを確かめる。

## 2026-08-08 「顔が写っているか」を見分ける道具の細かさを、合格ラインに書いていなかった
- 事象：素顔が残っていないことを「顔検出を掛けて0件」で判定していたが、
  **その検出をどの細かさで行うか**を合格ラインに書いていなかった。
  製品の実装は速さのため画面を幅960へ縮めて検出する。実測では、
  **90度回した顔は原寸なら1件見つかるのに、幅960へ縮めると0件**になる。
  つまり判定側を製品と同じ設定にすると「**実装が見落とす顔は、判定も見落とす**」ことになり、
  取りこぼしを一切検出できない検査になる。しかもテストは原寸を使っていたが、
  その選択は合格ラインのどこにも書かれておらず、次の人が変えられる状態だった。
- 根因：検出器を「道具」だと思っていた。実際には**判定の一部**であり、
  設定が変われば同じ動画が合格にも不合格にもなる。
  AGENTS.md が凍結を求める4項目（素材・数値・範囲・設定）のうち「設定」が空欄のままだった。
- 対処：判定に使う検出器は必ず素材の原寸で作る、と合格ラインに明記した。
  理由（実装より厳しい側に置く）と実測値も添えた。コード側も1か所に集め、
  呼ぶ側が縮小するかどうかを選べないようにした。
- 教訓：**判定に使う道具の設定は、合格ラインの一部として凍結する。**
  とくに「実装と同じ道具」を判定にも使うときは、
  **実装の弱点がそのまま判定の弱点になる**。判定は実装より厳しい側に置く。

## 2026-08-08 合格ラインの片側しか対照で固定していなかった
- 事象：「顔が隠れている」の合格ラインを、**隠れているときに値が高いこと**だけで確かめていた。
  「隠れていないときに低いこと」は、手元で1回測った数字を文章に書いただけだった。
  同じPRの別の条件では「10は通る／11は落ちる」と両側から挟んでいたのに、
  ここだけ規律が片側に緩んでいた。
- 根因：**対照を「壊れたときに落ちること」の確認としてだけ考えた。**
  合格ラインを凍結するには、上と下の両方から挟む必要がある。
  片側だけだと、ラインが「隠していない状態」より下にあっても気づけない。
- 対処：同じ実行の中で「誰も塗らない場所」（顔から離れた同じ大きさの矩形）の値を測り、
  下限がそれより上にあることを毎回確認するようにした。
  実測（塗らない場所5.00／正しく隠されている9.57）の中ほどへ下限を置き直した。
- 教訓：**数字を凍結するときは、上と下の両方を、同じ実行の中で測った値で挟む。**
  片側は文章に書いた実測値で済ませない。文章の数字は再実行されないので、
  環境が変わったときに黙って前提が崩れる。

## 2026-08-08 凍結した「つまみ」が、結果を決めていないつまみだった
- 事象：判定に使う顔検出の設定を凍結するため、「**検出器を素材の原寸で作る**」と合格ラインに書いた。
  ところが実装は検出のたびに入力サイズを**渡された画像の実寸で上書き**するため、
  **作るときの大きさは結果を一切決めていなかった**。
  書いたとおりに守っても、縮めた絵を渡せば今までどおり顔を見逃す検査にできる。
  さらに、理由として書いた「幅960に縮めると見つからない」も誤りで、実測では
  同じ幅960でも**間引き方**を変えれば見つかった（INTER_NEAREST で0件、INTER_LINEAR / INTER_AREA で1件）。
- 根因：**設定の名前を凍結して、設定の効き目を確かめなかった。**
  「この値を変えると結果が変わるか」を実際に動かして確認していれば、
  効かないつまみを凍結していることにすぐ気づけた。
  原因の切り分けも足りず、「縮小したから」で止めて「どう縮小したか」まで分けていなかった。
- 対処：凍結を「**判定は縮小していない原寸の絵そのものに掛ける**」へ書き直した。
  コード側も、渡された絵が素材の寸法と違えば0件と数えずにその場で落とすようにした。
- 教訓：**凍結する前に、そのつまみを実際に動かして結果が変わることを確かめる。**
  変わらないなら、それは凍結しても何も固定していない。
  そして**「Aだから結果がBになる」と書くときは、A以外を固定してAだけを動かして確かめる。**
  切り分けの粗い理由づけは、正しそうに見えるぶん、あとから誰も疑わない。

## 2026-08-08 対照の置き場所が、防ぎたい状態と別物だった
- 事象：「顔が隠れている」の下限を固定するため、「誰も塗らない場所」の値を対照にした。
  ところが選んだのは**無地の灰色の背景**で、防ぎたいのは「**顔がそのまま写っている**」状態だった。
  符号化ノイズの出方が違うため、無地は5.00なのに、実際の不合格側（顔がそのまま出ている状態）は

- 根因：「塗っていない場所」という**言葉の一致**で対照を選び、

- 対処：モザイクを一切掛けていない素材そのものと基準を、**同じ矩形・同じ式**で比べる形にした

  対照を選んだら「これは本当に、落としたい状態と同じ測られ方をするか」を一度問う。

## 2026-08-08 コードは直したのに、凍結する文章のほうを直し忘れた
- 事象：「合格ラインの対照が、防ぎたい状態と別物だった」という指摘を受けて**テストは直した**。
  ところが**ロードマップの合格ラインの文章は古いまま**残っていた。
  文章は「顔から離れた無地の四角で測り、実測5.00」、実装は「素材そのものと基準を比べて3.13」。
  同じ型の食い違いが、葉を割ったときにも起きた。
  「葉J-1 と葉J-2 に割った」と書きながら、J-1 の手順の中に J-2 の中身が3か所残り、
  同じ手順の中で「素顔が残ることは J-2 が受け持つ」と「素顔の存在も必ず測る」が同居していた。
- 根因：**直す対象を「動くもの（コード）」だと思っていた。** 凍結されるのは文章のほうで、
  独立検証者はコードではなく文章を読んで再実行する。
  コードを直した時点で「直った」と感じてしまい、文章との差分を確認する手順が無かった。
- 対処：文章を実装に合わせて書き直した。あわせて、割ったあとに残っていた旧IDの参照
  （「葉Jと同じ」「葉Aが要求しており」）も新しいIDへ更新した。
- 教訓：**コードを直したら、その直しが根拠にしている文章を必ず同じコミットで直す。**
  合格ラインは文章が正であり、コードはその実装にすぎない。
  とくに (1) 実測値を文章に書いているとき (2) 葉を割ったとき (3) 他の葉を名前で参照しているとき は、
  文章側が黙って古くなる。**割ったら、割られた側と割った側の両方を読み直す。**

## 2026-08-08 先に閉じる条件だけ、実行環境の凍結が抜けていた
- 事象：未着手の条件には「素材・失敗のさせ方・実行環境（OS・APIキーの有無）」を凍結したのに、
  **先に閉じようとしている条件**（画面から流して確かめるもの）には同じ凍結が無かった。
  この製品は文字起こしがAPIキーの有無で別のエンジンに切り替わり、
  どの区間を切り出すかはAIが毎回違う結果を返す。
  つまり**別の人が同じ手順で流しても、同じ合否にならない**状態だった。
  それなのに次の一手の欄には「実行者が選ぶ余地は残っていない」と書いていた。
- 根因：凍結の作業を「指摘された葉」に対してだけ行い、
  **同じ性質を持つ他の葉へ広げなかった**（同じ型の再発。今回で4回目）。
  しかも、先に閉じるもの＝すぐ検証されるものほど、凍結が甘いと実害が早く出る。
- 対処：画面から流す条件すべてに、素材・画面の設定・実行環境（ubuntu-24.04 / APIキー未設定 /
  python3 が使えること）を凍結した。AIが本数を決める部分は合否に含めず、
  「出来た全部について判定する。1本も出来なければ不成立」と書き切った。
- 教訓：**凍結の抜けは、先に閉じる条件から埋める。** 未着手の条件を丁寧に凍結しても、
  すぐ検証される条件が緩ければ、緩いほうから先に事故になる。
  作業の順序は「指摘された順」ではなく「実際に使われる順」で決める。
