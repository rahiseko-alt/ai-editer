概要

このファイル1個 ＝ ロードマップ（図）＋その仕様（README）の自己完結ファイル。 リポジトリにまずこれ1個あれば、ここから開始できる。用途は計画先行の進捗管理で、 アプリ開発でも任意の長期計画でも使える汎用の表。

案件の絶対起点：どんな依頼でも、実装より先にこの原子ツリーを作る（例外なし・AI裁量ゼロ）。 正の運用ルールはルート AGENTS.md「案件の絶対起点」。cc-v2 をコピーして始めた新案件は、 同梱ノードを破棄し新案件のゴールから描き直すのが第一コミット。

白紙テンプレ・モード（meta.template）

このリポジトリはテンプレ専用。コピー直後は meta.template:true／ツリーは白紙（ROOT 1個）で、 meta.handoff.nav に初回接続トップ手順ナビが入っている。運用フロー＝ コピー → 開く → チェックイン → nav を上から辿る → 原子ツリーを描き直す → meta.template を false → 実装開始。

  • meta.template:true の間は、機械（scripts/verify-roadmap-evidence.mjs）が「白紙ツリー」を許容する代わりに meta.handoff.nav を必須にする。
  • ツリーを描き直して meta.template を false にした瞬間、本物の原子ツリー（分解済み・criteria を持つ葉）の機械強制が自動で復活する。
  • ナビは上部バナーの「初回ナビ」に番号付きで表示される。

核となる仕組み（状態と作業）

上流＝状態（満たしたい結果）。下流＝作業（実行する操作）。作業を進めると状態が満たされる。

  • 状態ノード（state）：達成したい結果・条件。criteria（受入条件）を持つ。
  • 作業ノード（work）：具体的な操作。status＋commit/done_at を持つ。
  • 層数もタイプ名も固定しない。状態の中に状態でも作業でもぶら下げられる（再帰）。

完了ゲート（品質担保の心臓）

状態は「子が全部 done」だけでは done にしない。受入条件を検証し、証拠が付いて初めて done。

  • 作業ノード：実行して記録（commit/done_at）が残れば done。
  • 状態ノード：子が全部 done → 一旦 検証待ち（黄バッジ ⛔検証待ち）。受入条件が全て検証されて初めて done（赤字）。
  • これが作業→検証→状態成立の一方通行を作る。ここが無いと「子を全部やった＝一応OK」というタグだけ完了になり品質が抜ける。

受入条件（criteria）の書き方

条件は「動くこと」で書く。「ドキュメントがある／レビューした」で書かない。

  • 各条件は text（満たすべき状態）＋ verify（どう確かめるか＝人が読む手順の説明文）＋ verifyCmd（verify を機械が実行できる形にした具体的な1コマンド。任意だが、done化のゲートに必須）＋ evidence（結果の証拠＝commit SHA・CI run URL・デプロイID・公開URL 等の外部事実。スクショ等の自己申告は不可）。
  • evidence が空＝未検証（☐）。埋まって初めて充足（☑）。図の 受入 n/m バッジで進捗が見える。status:"done" なのに evidence が空のままだと scripts/verify-roadmap-evidence.mjs がCIで落とす（自己申告だけで完了扱いにできる穴を機械で塞ぐ）。
  • 証拠は「◯◯レビュー.md が存在する」を認めない。実物が動いた記録を指す。

基準を機械で下げさせない仕組み（2026-08-10 追加）

CIが緑・criteriaが凍結済みでも、それは「実装者が自分で書いたテストに自分の実装が通った」という自己申告の域を出ない。以下の3段で機械が閉じる。

  • ①凍結（scripts/verify-criteria-freeze.mjs）：着手前に固定した text/verify/verifyCmd は、その葉が status:"todo" 以外になった瞬間から無断で書き換え禁止。BASE/HEADのdocs/roadmap.htmlを比較し、正当な理由（meta.basisChangesに{id, criteriaHash, at, reason}を新規追加）が無い変更をCIで落とす。本文を書き換えず「葉ごと削除する」「一旦 todo に戻して直してからまた凍結し直す」という迂回路も同じ扱いで塞ぐ（reason: deleted / unfrozen）。
  • ②実行（scripts/verify-done-gate.mjs）：ある葉が今回のPRで新規に doing/todo → done へ遷移するとき、全 criteria に verifyCmd が設定されていることを必須化し、CIがそのコマンドを今この場で実際に実行して exit code 0 になることを要求する。「テストを書いた」という申告ではなく「このコミットで今まさに実行して合格した」という事実そのものをdoneの条件にする。過去に受理済み（BASEで既にdoneだった）葉には遡及しない＝既存ツリーは壊さず、新規のdone化から適用が始まる。
  • ③evidence（scripts/verify-roadmap-evidence.mjs）：①②を通過しても、最終的にevidenceへ外部事実（CI run URL等）を記入しない限りdoneは成立しない。
  • 正直な限界：①②③は「自己採点そのもの（テストを書かない／書いたが実行しない／実行したら実は落ちる）」を機械で閉じるが、「verifyCmdの中身がcriteria.textの要求を本当に厳密に検証しているか（境界値・対照実験の有無等）」までは exit code だけからは判定できない。ここは引き続き人間・独立サブエージェント（basis-reviewer／independent-verifier）の役目。

分解の規則（不変・自己相似）

最上位はゴール（最終到達状態）。以下、同じ規則を層の深さによらず当て続ける。

  • 不変の規則：P が成立する ⟺ 条件 C1…Cn が全て成立（各々が必要・合わせて十分）。これをどの層でも同じに当てる。層数は設計せず、当て続けた結果として出る。
  • 層は思考の分解粒度であって処理（工程）ではない。setup→deploy のような時系列は背骨に置かない（それは葉を辿る順番＝道順）。組織軸は「何が真であるべきか」。
  • 条件＝子ノード。まだ証明が要る条件は子の状態（自分の criteria を持つ）、直接確かめられる条件は葉の受入条件。再帰の底は必ず作業（操作）。
  • 個数は導出、粒度は選択：子の数は必要十分性から出る（設計しない）。どこまで割るか＝粒度は最初に1回決める計画の契約。

粒度の線：各葉の状態に、実行可能な verify が1つ書けるところまで割る。書けたら止める。その下（操作）は着手時に展開。

  • 浅すぎ＝目的が曖昧で検証不能。深すぎ＝過剰分解で麻痺。線は「意味の分解（何/なぜ）から行動の分解（どう）へ切り替わる高さ」に置く。
  • 機械強制（AI裁量ゼロ）：この粒度の線は scripts/verify-roadmap-evidence.mjs がCIで機械検査する。 子を持つ状態ノードに criteria を付けたら不合格、子を持たない状態ノードの criteria が0件でも2件以上でも不合格（＝ちょうど1件のみ許可）。 複数の受入事実を1葉に同居させることはできず、必ず独立した子の葉へ分割することになる。
  • 例外＝凍結した未来枝（status:"frozen"）：着手条件が揃うまで言語化分解しないと決めた枝は、 子も criteria も持たずにツリーの形だけ残す（機械検査もこの1点だけ除外する）。 凍結を解く＝status から frozen を外した瞬間に、原子分解と criteria 必須が自動で復活する。

網羅性の担保（複数軸の分解＋抜け漏れ検査）

単一の軸（機能面）だけで割ると、経路の一部や故障の型に対応する葉が構造的に漏れる。凍結前に複数軸を横断してから止める。

背景：2026-08-09、G-EDIT-CAPTION-AI（葉16個・basis-reviewer反証18件を反映済み）が、分解の軸が「AIに何をさせるか」の1本しか無かったために、実装後の外部レビューで実害のある欠陥4件を通した（docs/failures.md 2026-08-09参照）。以下はその再発防止として確立手法から翻訳した規則。

  • 軸1＝機能軸：「何をさせるか／させないか」という要求そのものを軸にした分解。これまでの分解はここだけで止まりがちだった。
  • 軸2＝経路軸（データフロー分解＋WBSの100%ルール）：対象のデータが入口から出口まで通る区間を一列に書き出す（例：入力→変換→外部呼び出し→応答→パース→適用→出力）。区間ごとに「子（葉）の合計が親（パイプライン全体）を100%説明しているか」を数える。葉の無い区間が1つでも残っていれば、分解は未完了。
  • 軸3＝故障モード軸（FMEA／FTA）：経路軸で列挙した各区間について「ここで何が壊れうるか」を機械的に問う（ボトムアップ＝FMEA）。定番カテゴリ＝プロセスの異常終了・出力形式の破損・想定外入力・タイムアウト・部分一致による誤検知。「この結果（例：字幕が誤って改変される）はなぜ起こりうるか」をAND/ORで逆算するFTAも併用すると、複合条件でしか起きない事故を拾える。
  • 軸4＝アクター軸：正規の利用者だけでなく、悪意ある入力を送る主体・外部サービス（AI呼び出し先等）自体の異常応答もアクターとして立てる。
  • 信頼境界を引く（STRIDEの簡易適用）：外部プロセス（AI等）の出力は「信頼できない入力」として扱う境界線を経路図に引き、境界を跨ぐ全区間に改ざん・異常終了の見逃し・情報漏洩の観点を要求する。

凍結前に抜けを検査する手順（basis-reviewer が使う）

  • 経路×観点のトレーサビリティ表を作る：縦軸＝経路の各区間、横軸＝観点（正常系／異常系／形式不正／プロセス異常終了／部分一致／権限外）。空欄セルがそのまま「未着手の受入事実」として可視化される。
  • プレモータム：「この機能はリリース後に重大インシデントを起こした。何が起きたか」を凍結前に問い、出てきた失敗の筋書きを上記の表に照らして漏れているセルを探す。
  • 敵対的レビュー：反証を出す自由演技の前に、経路の列挙とFMEAの故障モード確認を手順として踏む。「1本の軸だけで割っていないか」を最初に問う。

fixture（固定素材）は境界値分析で選ぶ

  • 「直ったことを見せる」だけの1パターンの素材を選ばない。対象パラメータ（例：置換対象語の出現回数）を同値クラスに分割し、境界（0回／1回／2回以上＝相互作用が起きる領域）を含む素材にする。
  • 複数パラメータが絡む場合はペアワイズ（任意の2パラメータの組み合わせ）で素材を設計し、単発の観点洗い出しでは気づきにくい相互作用ケースを拾う。

見積もりの粒度と根拠

  • 葉（ワークパッケージ相当）は着手判断ができる粒度まで割る（WBSの8/80時間ルールに準じ、規模に応じて調整する目安。絶対規則ではない）。
  • 見積もり根拠は前提・除外範囲・参照した過去実績を残す（Basis of Estimateの考え方）。単一の当てずっぽう数値だけを残さない。

割り方（計画先行・道順は都度）

目的地（状態）は先に全部描く。道順（作業）は着手時に割る。コミット1個サイズで止める。

  • 上流の状態は着手前に描き切る。下流の作業は、今の meta.active に着いてから分割・追記（遅延展開）。
  • 掘るときは「◯番を割って」→ その状態の受入条件を満たす作業へ、この規則で分割。
  • 作業1個＝1つの目的＝コミット単位。数は固定しない（2でも6でも）。

状態表示（文字色とバッジ）

  • 黒字 ＝ 未・着手中・検証待ち（todo / doing）
  • 赤字 ＝ 済（done）＝ 作業完了かつ受入条件を全て検証済み
  • 受入 m/m 全条件充足 ／ 受入 n/m 未充足あり ／ ⛔検証待ち 作業は済だが未検証
  • データ上は todo/doing/done/blocked の4値＋凍結の frozen（薄字＝着手条件が揃うまで分解しない未来枝）。親（状態）は子＋受入ゲートから自動導出（手動で done にしない）。

現在地・次の一手

meta.active（現在地ノードID）と meta.next（次の一手）を上部バナーに表示。セッション開始時に最初に読む値。

完了は git に紐付け（二重管理しない）

  • 完了の真実は git。作業完了時は status:"done" ＋ commit（短ハッシュ or PR）＋ done_at。
  • 状態の受入条件の evidence も commit SHA / CI run URL / デプロイID / 公開URL 等の外部事実を指す（スクショ等の自己申告は不可）。事実と食い違わせない。

データと表示の分離（重要）

ロードマップの正はこの HTML 内の JSON（<script id="roadmap-data">）。日々の更新はこの JSON だけを編集する。 状態・作業の判定と受入ゲートは末尾の描画エンジンが担う（モデルを変える時だけ触る）。

構造・インタラクション

  • 枠なしテキスト＋ツリー線（├─ └─）。1項目=2段（1段目 番号/種別/テーマ/（意味）/受入バッジ、2段目 詳細/完了日/commit）。
  • 折りたたみは <details>（子あり・受入条件ありはキャレット ▸、純粋な葉は非表示）。現在地は青丸の ✓ バッジ。
  • 階層は文字サイズ＋インデント＋接続線で区別（浅いほど大きい：d0=18px / d1=15 / d2=13 / d3=12）。
  • 図シートには解説を置かない（説明はこの README シートに集約）。
